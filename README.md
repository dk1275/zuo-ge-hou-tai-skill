# 做个后台 skill

一个面向 AI Agent 的通用后台搭建 Skill：帮助把内容管理后台做成可录入、可编辑、可预览、可审核、可发布、可回滚的完整生产系统。

它特别适合管理商场、地点、餐厅、攻略、商品、文章、家长投稿等“结构化资料 + 富文本/模块化内容 + 图片 + 审核状态”的后台，也适合从零搭建或修复已有后台。

## 这套 Skill 解决什么

很多后台看起来页面齐全，实际却会出现：

- 标题保存后再次编辑变空；
- 富文本或结构化模块被回填逻辑清掉；
- 预览内容与用户端展示不一致；
- 未登录能看到或写入管理页面；
- 编辑角色可以伪造审核者、状态或创建者字段；
- 连点保存产生重复记录；
- 审核通过后仍能重复审核；
- 投稿审核后没有正式内容，或正式内容没有出现在客户端；
- 图片上传成功但预览/客户端加载失败；
- 列表刷新、导入、分页导致重复行；
- 云函数显示“配置更新成功”，实际运行时仍是旧版本；
- 本地验证通过，却没有真实线上健康检查和回滚依据。

本 Skill 把这些问题归纳成同一条内容生产链，并要求 AI 在实现时同时考虑数据、权限、状态、媒体、预览和部署，而不是只补一个按钮。

## 核心原则

1. **服务端才是权限边界。** 前端隐藏按钮只是体验，不能代替接口鉴权、角色校验和字段白名单。
2. **一份 schema 贯穿全链路。** 表单、回填、预览、保存 payload、服务端校验和客户端展示不得各自发明字段。
3. **保存必须可重入。** 读旧记录、保护核心字段、锁定请求、按 ID 合并，避免空值覆盖和重复提交。
4. **富文本必须可逆。** 结构化模块有稳定 ID 和类型；未知字段有保留策略；失败时保留草稿。
5. **H5 预览是共用渲染出口。** 编辑后实时更新，直接消费编辑态规范化模型，不等待保存，不复制一套保存逻辑。
6. **审核是状态机。** 审核、发布、正式内容、审核日志要有明确迁移和原子性/补偿方案。
7. **媒体是业务数据。** 上传限制、私有/公开边界、稳定引用、短期访问和清理路径都要设计。
8. **线上事实优先。** 部署后读取线上配置和版本摘要，不能只相信 CLI 的成功文案。

## 共用的 H5 编辑预览

这是本 Skill 的重点能力：后台编辑栏左侧录入，右侧或下方直接显示 H5/移动端详情页效果。它不是一张静态 mock，也不是保存后重新拉取的详情页，而是同一份编辑态数据的实时渲染。

```text
输入/选择/模块变化/图片变化
              ↓
       规范化 PreviewModel
              ↓
       H5 Preview Renderer
              ↓
  手机端布局 + 真实内容结构 + 临时图片
```

通用实现要求：

- 所有内容类型共用 `buildPreviewModel()` 和预览容器；商场、地点、餐厅、文章的差异放在模块 renderer。
- `input` 和 `change` 事件立即刷新预览；草稿自动保存可以防抖，但预览不能等云端响应。
- 预览必须读取当前编辑态，不能读取打开弹窗时的旧列表对象。
- 结构化模块、富文本、标签、关联对象、排序和图片都必须实时反映。
- 本地图片使用临时 object URL/data URL 预览，上传成功后再替换成稳定媒体引用；临时引用不得落库。
- H5 预览只读，不触发真实收藏、分享、导航、发布、审核或删除。
- 桌面端左右分栏，移动端上下排列；预览区独立滚动，保存/发布操作始终可见。
- 关闭并重新打开编辑器时，表单和预览都从草稿/云端回填，不能因为重建 DOM 丢失字段。

推荐统一预览模型：

```js
{
  title, subtitle, cover, gallery, meta, tags,
  summary, body, blocks, actions, status
}
```

这样另一个后台只需替换实体字段映射和模块 renderer，就能复用同一套编辑态预览、回填、防丢失和验收方法。

## 推荐使用方式

把本仓库作为 Skill 安装后，向 Agent 提供：

```text
请使用做个后台 skill 搭建这个管理后台。
先读取项目地图，梳理实体、状态、角色和媒体边界；
再实现最小完整闭环：登录、列表、编辑、预览、保存、审核、发布、删除和部署验收。
不要只做 UI，交付时区分已实现、已验证、已部署和待人工验收。
```

如果是修 bug：

```text
请使用做个后台 skill 排查“编辑后内容丢失”。
先定位 schema、回填、payload、服务端保存和云端回读链路，
给出根因、最小修复、回归测试和线上验证，不要用本地假数据掩盖失败。
```

## 从实际项目中总结的坑位

### 富文本和回填

最难发现的问题不是输入，而是“再次打开”：编辑器异步初始化、字段名称不一致、空默认值覆盖旧数据、历史字符串/数组不兼容，都会让标题或正文看似保存成功却重新变空。解决方式是统一领域对象、编辑前读取旧记录、关键字段空值保护、保存后云端回读，并把“关闭再打开”作为固定回归用例。

结构化攻略还会遇到 JSON 键顺序、旧字段和布尔值形态造成的误报。不能比较序列化字符串，应先规范化后比较语义；模块必须保留稳定 ID、顺序和关联目标。

### 权限和审核

管理页面可以加载出来，不代表已安全。曾经最容易踩的是：初始同步失败却解锁页面、前端传入角色/状态被服务端直接写入、已审核记录还能再次审核、投稿状态变了但正式内容或日志没同步。解决方式是登录失败保持锁定，服务端重算身份和状态，保护系统字段，审核采用明确状态机，并在同一事务或补偿流程完成正式内容、投稿状态和日志。

### 保存和重复提交

用户连续点击保存、网络超时重试、分页刷新和导入合并都会制造重复数据。不能只在按钮上加 loading；要在前端请求锁、服务端幂等/版本控制、按 ID 合并和云端回读四层同时防守。错误时保留表单，不能追加本地假记录。

### 图片和预览

临时文件、私有引用和公开 URL 混用会造成“后台有图、小程序没图”。媒体应有统一引用格式和访问策略：投稿图片先私有，审核通过后才进入公开内容；预览直接消费规范化模型，上传完成后使用稳定引用；渲染失败显示占位和错误，而不是把整张卡片撑坏。

### 部署和运行时

部分云函数的 Runtime 只能在首次创建时确定，普通配置更新或代码部署不会迁移存量 Runtime。若尚未上线，应 dry-run 核对目标、保留源码和配置，再删除并重建同名函数，最后用线上详情和真实调用验证。若已经上线，则需要维护窗口、回滚版本和数据兼容方案，不能直接删除生产函数。

## 交付标准

一个后台只有同时满足以下条件，才可称为“完成”：

- 正常路径可新增、编辑、回填、预览、审核、发布和删除；
- 空值、非法参数、越权、重复提交、超时、找不到记录和重复审核都有明确处理；
- 富文本、结构化模块和图片不会因重开编辑器而丢失；
- 管理接口没有匿名写入，服务端权限不依赖前端按钮；
- 线上配置、代码版本、运行时和触发器已真实核验；
- 有可执行的回滚依据；
- 报告区分已实现、已验证、已部署和待人工验收。

## 安全边界

本仓库不包含任何项目密钥、密码、真实用户标识、生产环境 ID 或业务数据。使用者仍需根据自己的认证系统、存储服务和部署平台补齐配置，并在实际发布前完成人工验收。
